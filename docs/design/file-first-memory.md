# 以文件为真相的实体记忆方案

状态：设计提案，2026-11-14。本文中的新增字段与检索行为尚未实现；当前实现以 `docs/architecture.md` 为准。

## 目标与结论

让 agent 在换会话、换宿主后认出同一台设备、同一个项目，找到与当前问题相关的事实与经历，并使用用户已经熟悉的领域帮助解释。用户无需管理节点、维护关系类型或启用额外服务。

建议采用 Markdown 记忆文件、稳定实体身份、文件内实体引用和可重建的 SQLite 索引。先连接「实体与讲述这个实体的记忆」，暂不引入通用三元组系统、单独的关系文件库或图数据库。

记忆正文保留自然语言的原因、条件和上下文。例如「项目由于部署约束选择 SQLite」比只有「项目—使用—SQLite」更能帮助后续决策。结构化引用只补充检索所需的身份信息。

| 方案 | 本阶段取舍 |
|---|---|
| 每个事实、关系各一个文件 | 更新一段经历会涉及多文件一致性，容易把上下文拆散，暂不采用 |
| 独立关系 JSONL 或全局图文件 | 为同一份知识增加另一套写入、备份与纠正流程，暂不采用 |
| 记忆正文加实体引用 | 内容和关联一起原子更新，关系反查从文件派生，作为第一版方案 |

## 当前实现与缺口

- `entities` 已是一实体一文件，文件名由 `name` 决定；尚无稳定的跨改名实体标识和别名解析。
- 文件 frontmatter 保存 `sources`、材料时间与版本关系；自动交付已有回执机制。
- `memory_link` 的 `derived_from` 能从文件 `sources` 重建；其它类型尚无文件真相，需迁移。
- 当前记忆 YAML 编解码只覆盖标量与字符串数组；序列化只保留已知字段。添加字段必须贯穿解析、写入、复核、版本、合并与重建，不能只改抽取提示词。
- 当前 `reindex` 重建检索、向量与来源边，不负责整库账号、组成员或完整授权恢复。不得将「记忆能恢复」表述为「整个数据库可随时删除」。

## 文件内容与粒度

继续使用已有记忆类型：实体文件保存稳定描述和当前状态，事件文件保存重要变化，经验文件保存适用条件与做法。单条事实不强制拆文件；也不把所有设备或项目内容塞进一个画像。

建议的新增字段只有三类：实体文件的 `entity_id` 与 `aliases`，记忆文件的 `entity_refs`。以下只展示拟新增字段和正文，省略现有状态、来源、时间等必需字段：

```yaml
# entities/thinkbook.md 的 frontmatter
entity_id: 7bf26c44-9280-4e21-9b87-8a3c697e6240
aliases:
  - ThinkBook
  - 联想笔记本
```

正文仍然写「这是用户的主力笔记本，当前使用 Arch Linux」等完整描述，不为每个操作系统版本创建节点。

```yaml
# experiences/laptop-installation.md 的 frontmatter
entity_refs:
  - 7bf26c44-9280-4e21-9b87-8a3c697e6240
```

该经验的正文保留安装步骤、失败原因和限制；它只需明确自己讲的是哪台设备。

`entity_id`、`entity_refs` 是受服务端校验和维护的保留元数据，`aliases` 是实体类型的字符串数组字段。它们的解析、投影和序列化应在现有记忆链路内闭合，不扩展通用 YAML 子集去支持任意深层对象。引用只允许服务端确认过的实体编号映射结果，不让模型自由编造 UUID。

`entity_id` 由服务端生成并保存在文件中，不取决于名称、路径或正文摘要。名称、路径确实会改变，因此不能把相似名称或新的路径当成新的实体。已有 `comem://` 继续作为访问地址与授权边界，实体 ID 不构成第二套访问协议。

索引保存 ID 到当前 URI 的映射。移动实体文件保留 ID，引用无需批量改写。复制成独立实体必须生成新 ID；发现重复 ID 时报告文件冲突，不任选一个。跨个人/团队空间复制默认属于独立记忆；显式共享引用保留原 ID，并按引用目标当前权限读取。

实体引用只表示「这条记忆与这个实体有关」，不自动证明拥有、隶属、因果等关系。人类或模型仍需阅读正文理解关系。身份无法确定时允许暂不关联，保留有来源的自然语言内容。

名称和别名都不是唯一键。两台 ThinkBook、两个同名项目可以同时存在，索引必须返回候选集合；只有明确身份与上下文支持时才选定实体。人无需为使用功能维护 ID，控制台与 agent 仍显示名称和 URI。

## 写入与纠正

1. 复用现有归档抽取调用，提供同作用域内已有实体候选；不要额外增加每轮在线模型调用。
2. 候选先按已知 ID、名称、明确别名查找，再用 embedding 帮助提供候选。向量相似只用于找候选，不直接决定合并。
3. 模型继续引用服务端提供的页面编号；同批新增实体先分配稳定 ID，再解析其它新记忆的引用。不存在或未提供的目标编号不能被编造成有效实体。
4. 人物、设备和项目的指代结合最近对话、明确陈述与来源环境判断。「我的电脑」「这台机器」是上下文指代，不写成全局别名；当前命令运行环境也不能自动等同于用户主力电脑。
5. 在文件路径锁内校验并原子保存文件，再按该文件的完整当前状态替换派生索引。删除引用必须删除对应索引行，不能只追加边。
6. 文件写成而索引失败时记录待修复操作，后续重放；文件失败不发布新索引。同批目标缺失时保留可诊断的引用，不以它生成确定上下文。

人工纠正与旧材料保护继续沿用现有链路。第一版仍是节点级材料时间，不能宣称已具备事实级时间推理。重要状态变化使用现有事件和版本记录；尚不引入给每个属性建立独立事件流的体系。

稳定 ID 也不等于语义遗忘已经解决。当前删除屏障按 URI/子树保存；加入实体身份后，应同时记录已删除实体 ID，阻止旧引用把被删实体重新挂回，且不能因重命名绕过。对来自新材料的显式重新记忆保留恢复路径；无法识别为同一实体的不同表述仍是已知限制。

消歧出错需要可纠正：允许把某条记忆的 `entity_refs` 从错误实体移到正确实体，保留原文与来源，不要求重跑全部历史。合并实体先保留原始 ID 的可追踪映射，不在本阶段做不可恢复的自动合并；用户说「这是另一台电脑」时应能拆开引用。

解析和序列化要有一份字段契约，覆盖普通编辑、自动更新、复核、版本回退、合并与手工文件重读。不能让用户加了 `entity_refs` 后，下一次后台更新又把它丢掉。

## 召回方式

保留当前有界的基础背景：熟悉领域和解释偏好可直接帮助回答。设备细节、项目经历仍按问题召回，避免以一份越来越大的画像代替检索。

检索在同一预算内合并三种候选来源：

- embedding 与 FTS5 提供语义和精确词候选。
- 当前问题和最近对话能够明确解析的实体，提供该实体的当前描述。
- 已确定的具体实体提供与其关联的记忆候选，结合原问题筛选。

第三步是「经过一个实体找到相关记忆」的一层实体邻域；在二部图上经过两条边，不称为任意多跳推理。它只扩充候选，候选不自动全部注入，也不把原候选分数直接复制给邻居。沿用现有融合、上下文组装、时间预算、token 配额与回执流程，不增加未经说明的图分数系数。

无法明确解析实体时退回正常语义检索，不为了走图而强行选一个。询问当前环境时，优先交付实体的当前状态；关联到的历史事件保留「当时」的表述，不凭相关度把旧系统重新当成现状。历史问题可以查事件与版本，但本提案不承诺任意事实的时间推理。

「用户」「软件」「Linux」等常见词不能成为展开整个记忆库的通道。第一版只围绕明确的人物、设备、项目等具体实体扩展，且不递归走来源边。实体引用索引只存「记忆到实体」，不把所有共享实体的记忆两两存边。

每次查询按当前权限解析目标 URI，显式范围保持收窄；读取关联记忆前继续求权。个人与团队同名实体不自动合并。共享记忆中的设备属于谁、规则适用于哪个项目，由正文与明确来源表达，不能根据谁能读到它推定事实归属。

## 什么时候再增加带类型的关系

当已有具体问题需要跨多个实体回答，例如「这个项目依赖哪个服务，服务故障会影响哪些部署」，再增加带谓词的关系事实。关系仍需有文件真相、明确来源、适用时间与失效路径。

当前先验证「同一实体的多次经历能被找齐」和「自然语言里的关系能被正确使用」。这一阶段不建立通用关系本体，不为所有名词自动创建节点，不为实体共现推断拥有或因果。

## 迁移与恢复

先补齐文件真相，再启用新检索行为：

1. 已有实体文件逐步补稳定 ID，缺 ID 的旧文件仍可正常读取和语义检索；第一次增补在锁内幂等完成，不按相同名字自动合并旧实体。
2. 既有数据库独有的 `references` / `related` 先导出成文件内显式记录，保留原类型、说明与出处。它们不自动等同于实体引用或业务关系；不存在的起点也要导出到可检查的文件清单，不能静默丢弃。导出清单只是迁移材料，不能当成新的全局关系库；未转入可解析的正式文件格式前，不得宣称此类边已经能从记忆文件重建。
3. 在隔离目录验证迁移后的文件可独立重建，再切换写路径为文件优先。原数据库保留备份，迁移不能以先删表开始。
4. 重建流程区分结构索引和向量重算。实体身份、别名、引用与来源的结构索引应能离线、零生成模型调用恢复；重建向量可能需要 embedding 和时间，不承诺零成本。
5. 记忆备份保留实体、事件、版本、源材料、ACL 与删除记录。完整服务备份还需要账号、组成员、凭据及运行配置；数据库中这些数据不因增加实体索引而变成可丢弃缓存。

手工修改文件后的可见性也需明确：服务内编辑立即更新索引，外部编辑在重建后生效。当前不以新增文件监听、跨机器同步或 Git 自动合并扩大范围。

## 实施顺序与验收

按用户偏好先实现，再补针对完整行为的测试，不先搭基线测量平台。

| 阶段 | 改动 | 验收 |
|---|---|---|
| 1. 文件完整性 | 字段往返、稳定身份、旧边导出、可重建结构索引 | 隔离新库仅凭文件恢复一致的 ID、引用、来源；版本回退不丢新增字段 |
| 2. 写入闭合 | 抽取关联、候选消歧、更新、移动、删除、合并、补偿 | 同设备不同称呼能关联；不同设备不误合并；故障重放不会制造重复 ID 或残留旧引用 |
| 3. 实体辅助召回 | 有界实体邻域与现有自动上下文合并 | 新会话询问安装方式能结合正确设备；更新系统后不用旧状态；团队同名设备与无关知识不冒充个人背景 |

实施接缝控制在现有链路：记忆字段与序列化、抽取编号映射与归档产物、记忆更新/复核/版本/合并、文件观察者与重建、检索组装。新增实体引用不能只留在进程内，必须随抽取产物落盘，任务重试后仍能恢复同一组 ID；这些都完成后才启用关联候选。

运行真实文件与 SQLite 的集成回归，以及现有 typecheck、lint、配置消费、可达性、形状和文档检查。确定性模型响应可以验证接线与故障语义；真实模型是否识别准确、使用自然，需单独记录真实使用证据，不以测试总数代替。
