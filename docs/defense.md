# 答辩材料

这份材料按「照着讲」写：第 2 节是 8 分钟演示的分镜，第 3 节是六个设计决策的口播稿，
第 4 节是可能被追问的问题。所有数字与结论都能在
[`architecture.md`](architecture.md) 的对应小节或仓库里的测试找到出处。

## 1. 一句话定位（30 秒）

> CoMem 是给 AI agent 用的上下文记忆数据库。它给每条记忆一个稳定地址
> `comem://user/alice/memories/preferences/no-any.md`，让 agent 在不同会话、不同机器、
> 不同队友之间共享「它知道的东西」。
>
> 内容是真的 Markdown 文件，索引在 SQLite FTS5 里，对外是一个 HTTP API、16 个 MCP 工具
> 和一套 Nuxt 控制台。会话集成走六个 Hook 插件，装在 Claude Code 或 DSH 里。
>
> 一句话概括取舍：**v1 用词法检索换掉向量检索，把力气花在「检索结果怎么进模型上下文」上**
> ——预算、分层、去重、配额。

## 3. 六个设计决策（每个 60 秒）

### ① 内容存文件系统，索引存 SQLite

**选了什么**：记忆、摘要、权限、会话消息全部是真实文件（Markdown + YAML frontmatter +
`messages.jsonl`），SQLite 只存「从内容算出来的东西」（倒排索引、物化的有效权限、任务行、
请求记录）。

**放弃了什么**：跨文件事务。写文件和写索引不是一个事务，可能不一致。

**为什么**：三条。第一，**删库不丢数据**——`rm _meta/comem.sqlite` 之后，Markdown 的摘要
从 frontmatter 读回来，重建过程零模型调用；摘要在库里就要花钱重算，权限在库里就是所有人
失去访问权。**但要诚实**：重建命令（`reindex`）还没实现，所以这条现在只是设计承诺，
不是能跑的运维流程（见第 5 节）。第二，**目录删了不留孤儿**——文件摘要在文件里，`rm -r`
之后不会留下指向不存在节点的索引行。第三，**人可以直接改**——断网、模型挂了、摘要写错了，
用编辑器改 `.overview.md` 就能修。

**代价怎么兜**：批量导入时索引写失败会往 `_meta/reconcile.log` 追加一条；补偿方向是
「把索引追上来」，不是「把文件退回去」——文件已经是对的，回滚反而丢数据（§7、§10.6）。
**重放同样没有实现**，日志只是线索。

**评委可能追问**：那不就最终一致了吗？是。所以「检索不到刚写的内容」被列进排障手册，
`reconcile.log` 是第一条要看的地方。

### ② L0 / L1 / L2 渐进披露

**选了什么**：同一份内容有三种粒度。L0 是目录的 `.abstract.md`（预算 256 字符），
L1 是 `.overview.md`（4000 字符），L2 是原文。检索先给 L0，模型判断相关再升到 L1 / L2。

**放弃了什么**：把命中的原文直接塞给模型。

**为什么**：上下文窗口是稀缺资源，而命中列表里大部分条目只相关一次。没有分层的话，
10 条命中就要把 10 份原文塞进去，其中 8 份是浪费——而且模型会因为这些细节分心。
分层还解决了一个具体问题：**L0 摘要本身就是检索的召回单元**，所以「我不记得在哪个文件，
但记得有这回事」这种查询能命中目录（§8.6、§9.1）。

**这一层的边界**：L0 从 L1 正文里提取，两层不会互相矛盾；L0 只从 L1 的第一段取，
因为那是「一句话说清」的位置。

### ③ 目录级检索 + 层级加权（不是平铺的向量检索）

**选了什么**：FTS5 + BM25 词法召回，四个面 `find` / `search` / `grep` / `glob`；
排序分 = `bm25 × 层级权重`（L0 1.15 / L1 1.05 / L2 1.00）。

**放弃了什么**：语义召回。同样问「怎么写认证」，词法检索靠 `authentication` 这个词命中，
换个说法就命中不了。

**为什么**：词法检索零依赖、离线、可解释（分数能算出来）、写入即时可见。层级加权是
「不给向量库也能改善排序」的手段：L0 摘要经过一次人工或模型的压缩，信噪比天生比 L2 高，
所以在词频接近时应该赢。**权重只用来打破平局**——1.15 意味着 L0 词频不差太多就能赢 L2；
L2 词频明显更高时仍然应该赢（§8.5）。

**代价**：同义改写的召回是 v1 的明确短板，接口留好了（`RetrievalIndex`，§4.4），
换后端不改上层。

### ④ 记忆抽取走「预取 + 补丁合并」

**选了什么**：提交时先按记忆类型的目录做一次检索，把 top-N 命中塞进 prompt，模型**单次**
输出「URI + 字段级合并操作」（patch / replace / sum / immutable），服务端再按 URI 合并。

**放弃了什么**：让模型直接写文件（省掉合并），以及 reAct 循环（先 `search` 再 `read`，
最多 3 轮）。

**为什么**：直接写文件有两个硬伤。第一，**同 URI 的多条操作会互相覆盖**——一次提交可能
产出 20 条操作，其中 5 条指向同一个记忆文件，5 次覆盖写最后只剩最后一次。补丁合并把
「同一字段的多条 patch 按顺序应用」交给确定性的字符串逻辑，不调模型。第二，**模型看不到
已有记忆就判断不了「这是新增还是更新」**，只能盲目新增，结果是大量重复；预取解决这个问题
且比 reAct 省 token。

**一个关键约束**：SEARCH 必须**唯一**命中。命中零处或多处整条操作失败、记进
`skippedOperations`，**不做模糊匹配**——猜错的代价是静默改坏一条记忆，比报错严重得多
（§11.2、§11.5）。

### ⑤ ACL 不进 MCP

**选了什么**：16 个 MCP 工具里没有 `get_acl` / `set_acl`。ACL 只走 Web 与 HTTP，而且读写
都要求 `manage`。

**放弃了什么**：agent 自己管权限的能力。

**为什么**：**一个能给自己授权的 agent 就是提权漏洞。** 模型被提示词注入控制时，第一件
想做的事就是给自己加权限；把授权面从 MCP 拿掉，这条路径直接不存在。管理面还有两个入口
（`grant` / `revoke`）是 HTTP 的语法糖，但它们最终都走 `setAcl`，所以「写 `.acl.json` →
重算整棵子树」只有一份实现（§12.2、§12.4）。

**顺带的不变量**：owner 恒 `manage`，不能被 ACL 收回——否则存在「先收回 owner 权限、
再借别人的路径提权」的路径。同节点 `deny` 优先。

### ⑥ 摘要失效用 digest 比较（不是每次重算）

**选了什么**：写节点时算 L0 正文的 digest，与索引里记录的比较；**一样就到此为止**，
不一样才向父目录传播，并累加 `pendingChanges`。

**放弃了什么**：全量重算（每次写都重算整条祖先链），以及「脏标记」（一个布尔位）。

**为什么**：全量重算的代价随目录深度线性增长；而脏标记有个致命问题——**同一个文件反复改，
脏标记只算一次，永远到不了重算阈值**。事件计数才反映「这个目录的摘要落后了多少次改动」。
阈值是：小目录（≤ 32 条）立刻重算，或 `pendingChanges / totalEntries ≥ 0.10` 立刻重算，
否则只记脏等下次（§9.3）。

**消费时减而不是清零**：重算过程中可能又有新改动进来，写回时
`pending = max(pending - 消费时的快照, 0)`，生成期间到达的改动保留。

## 4. 可能被问到的 15 个问题

**1. 为什么不用向量检索？**

v1 用 FTS5 + BM25 换掉向量：零额外依赖、离线可跑、分数可解释、写入即时可见（没有索引
延迟）。向量需要 embedding 服务、模型版本与维度管理、相似度阈值难定，而且冷启动要全量
重算。接口留了（`domain/retrieval.ts` 的 `RetrievalIndex`），换后端不改上层。**明确弱点**：
同义改写召回不到，这是取舍不是遗漏。

**2. 摘要失效怎么保证一致？**

三层。① 写节点时算 L0 正文 digest，与索引里记录的比较，一样就不传播——同一个内容重复写
不触发重算。② 变了才累加父目录的 `pendingChanges`，按「≤32 条」或「比例 ≥ 0.10」决定立刻
重算还是只记脏。③ 重算完成后若父目录的 L0 正文也变了，继续向上，到 scope 根停。
「消费减而非清零」保证生成期间到达的改动不丢。**边界**：这是最终一致，不是强一致；
`.abstract.md` 本质是可手改的缓存。测试在
`tests/integration/sqlite/summary-freshness.test.ts` 与 `tests/integration/services/summary.test.ts`。

**3. 记忆抽取的准确率怎么测？**

**还没测。** 没有标注集，也没有离线评测。现在能保证的是工程正确性：输出是 zod 结构化
schema、解析失败重试一次、截断（`finishReason = length`）**不**重试（同样的上限只会再截断
一次）、越界 `page_id` 进 `skipped` 而不是抛错、每次归档写 `memory_diff.json` 记录
adds / updates / deletes / skipped。要真测，需要一批真实会话 + 人工标注的期望操作 +
按字段比较，这是 backlog。

**4. 并发写同一个文件怎么办？**

路径锁，两种模式：`EXACT` 锁单文件（`write` / `edit`），`TREE` 锁子树（`rm -r` / `mv` /
目录级写）。实现是 `{path}.comem-lock` 文件，内容是 `{owner, expiresAt}`，30 秒租约、
10 秒续租，释放时校验 owner。锁文件用「临时文件 + hard link」原子创建，不用
`writeFile(..., 'wx')`——后者从创建到写入之间有一个空文件窗口，并发读方会把它当成损坏的
锁抢走。`move` 对互为祖先的路径直接抛 `INVALID_ARGUMENT`，否则第二把锁会等自己。
另外 `edit` 用 `expectedDigest` 做乐观并发：读到的正文和写回的正文之间被人插过就
`CONFLICT`（§10.6）。

**5. 模型不可用时会怎样？**

看链路。**摘要**：降级到 `RuleSummarizer`（子节点名字 + 摘要首句拼接），结果带
`degraded: true`，`/health` 报 `degraded`，控制台显示——降级必须可见。**抽取**：重试一次
后抛 `PROVIDER_UNAVAILABLE`，任务置 `failed`（最多 3 次），`.done` 不写，归档可以重放
（`stepsDone` 跳过已完成步骤）。**检索**：完全不依赖模型，`find` / `grep` / `glob` 是纯
SQL + 文件读取。**演示**：整个 `scripts/demo.sh` 用 `summary.generator: rule`，不需要任何
模型凭据。

**6. 为什么是 16 个 MCP 工具，多一个不行？**

工具描述进模型上下文，每个都有 token 成本，而且工具越多选错概率越高。16 个是按使用场景
划分的结果：10 个只读（`find` `search` `rule_search` `read` `list` `tree` `grep` `glob`
`download` `health`）、4 个写（`write` `edit` `remember` `forget`）、2 个摄取
（`add_resource` `add_skill`）。这是硬约束，`ToolRegistry.validate()` 在启动时检查数量 /
重名 / 白名单，多一个少一个都启动失败（`AGENTS.md`）。**故意不做的**：ACL（提权面）、
用户与组管理（管理面）、隐私占位符 / MCP 联邦 / watch（范围外）。

**7. L0/L1 的 256 / 4000 字符是怎么定的？**

来源是 §9.1 的预算表，**是经验值，没有推导**。256 大约是「一句话 + 一个短句」，够判断
相关性；4000 大约是一页半，能替代大部分原文阅读。两个都可配置
（`summary.abstractMaxChars` / `overviewMaxChars`），超预算截断、不重试。要定得更好需要
一批真实查询做对比实验，这部分没做。

**8. 中文检索为什么用 unigram 分词？**

实测（SQLite 3.54.1，Node 26 的 `node:sqlite`）：只用 `unicode61` 时，连续中文被当成一个
巨型 token，搜「记忆」0 条；只用 `trigram` 时要求查询 ≥ 3 字符，而中文双字词是最常见的
形式（「用户」「偏好」「记忆」全部落空）。**CJK 单字切分 + 查询侧同样切分后包成短语**两者
都命中。代价是单字拉低 BM25 的区分度（「的」「在」到处都是），靠「短语要求字符相邻」的
约束 + 层级加权顶住。索引里存的是切分后的文本，不是原文——它只服务匹配，`read` / `grep`
走文件系统（§8.1）。

**9. 为什么摘要是目录级的，而不是文件级？**

两个层次都有，各管一件事。**文件级**摘要写在文件自己的 frontmatter 里（`summary` /
`summary_digest` / `summary_state`），跟着文件走：移动、复制、备份都不用额外维护，重建
索引时扫一遍文件头就行，一次模型都不调。**目录级** L0/L1 回答「这个目录里有什么」，是
检索的召回单元。边界：只有 Markdown 支持 frontmatter（代码、JSON 没有统一语法），这类
文件的摘要存索引的 `abstract` 字段，重建时重算（§6.7、§9.1）。

**10. 为什么 `.done` 要最后写？**

它是**唯一的完成信号**。先写就等于宣称成功，而后面步骤可能什么都没做。重放时的判据在
`.meta.json` 的 `stepsDone`：每步完成立刻落盘，因为记忆操作**不幂等**——重放一次 patch，
SEARCH 可能还能匹配，结果是同一段事实被写第二遍。所以崩溃恢复的正确性依赖「步骤级记录 +
`.done` 最后写」这对组合（§10.1）。

**11. 为什么要物化 `node_permission`，每次读 `.acl.json` 不行吗？**

不行，两个硬伤。① 一条候选要 open 5 层目录的 `.acl.json`，`tree` 一个 1000 节点的目录
就是 5000 次文件读。② 如果取回的前 40 条候选全都没权限，最终返回不足 10 条——用户看到
「没有结果」，而实际上有。所以把「这个节点对谁能做什么」在写 ACL 时算好，检索时是一个
`EXISTS` 子查询。方向是「写时算、读时查」：ACL 改动低频，检索高频。代价是改一个节点的
ACL 要用事务重算整棵子树（§8.2）。

**12. 检索分数为什么这么小，是 bug 吗？**

不是。分数 = `-bm25` × 层级权重，**没有归一化**。FTS5 的 `bm25()` 返回负数（越小越相关），
取负之后越大越相关，量级随语料规模变化。所以：同一个查询的结果之间可比，不同查询之间
不可比。目录行（L0）文本短、词频低，分数接近 0 是正常的。`scoreThreshold` 是绝对分，
跨查询不稳定——这是 v1 的已知弱点，归一化或 rerank 在 backlog。

**13. 为什么是单用户？多租户差什么？**

差「每请求一份服务图」。`Authorizer` 的三个方法没有 subject 参数，`Container.services`
只有一份，`HttpRouteGroup.register(app)` 也拿不到请求——服务图在启动时绑定一个身份。
v1 用 `x-comem-subject`，但它**必须等于**绑定身份，不一致直接 401：静默换成绑定的身份就是
冒充。多租户要真正的认证 + 每请求一份服务图，这是 v1 明确不做的范围（§2、§12.4）。

**14. 数据会不会丢？怎么备份？**

内容文件是真相，SQLite 是派生；写入是原子的（临时文件 + rename），批量导入时索引写失败会
往 `reconcile.log` 追加一条——**但重放和 `reindex` 都没实现**，所以「删库可重建」现在只是
设计承诺，备份必须把整个数据根打包，不能只备份内容文件。具体步骤见
[`operations.md`](operations.md)「备份与恢复」。另外三个已知小坑：`reject` 的原因只进日志、
`request_log` 没有清理任务、`download` 的签名密钥是进程级随机值（重启即失效）。

**15. 为什么 Hook 插件不写成 MCP 工具？**

MCP 工具是**模型主动调用**的。会话提交不能靠模型「记得调」——它一忘，这次对话就丢了；
而且提交要在**每轮结束后**发生，模型没有这个时机。宿主 Hook 是固定的生命周期点：
`SessionStart` 注入 profile 与技能目录、`UserPromptSubmit` 召回、`PostToolUse` 采集工具
调用、`Stop` 采集并提交。采集跑在分离的 worker 进程里，`Stop` 立刻返回——卡住等于把用户
的输入延迟绑在模型抽取上，抽取一次几秒到几十秒（§15.1、§15.3）。

## 5. 还没做的（backlog）

按「现在最疼」排序。前两条是**已知会挡住演示**的，主动说。

| 项 | 现状 | 为什么先不做 |
|---|---|---|
| 常驻任务执行器 | 阶段二的四个步骤有实现、有测试，没有进程 `claim` 任务，归档后任务停在 `pending` | 需要常驻循环 + 租约心跳；演示脚本能绕过（见第 2 节步骤 4） |
| 多租户 / 第二个身份 | 服务图绑定单身份，组空间建不出来 | 要真正的认证 + 每请求一份服务图，是另一套装配 |
| `reindex` 重建命令 | 没有。索引坏了只能靠文件系统继续读写 | 运维场景，演示用不到；但「删库可重建」的承诺因此暂时兑现不了 |
| `reconcile.log` 重放 | 日志在写，没有启动扫描去重放 | 和上一条是同一件事的两半：一个负责「记下来」，一个负责「补回去」 |
| 快照与回滚 | 没有 | 归档级回滚（按 `memory_diff.json` 反向应用）比 git 风格快照便宜，仍是 P2 之后 |
| 空闲提交扫描器 | 没有 | 需要常驻定时器，长会话场景才需要 |
| Rerank | 没有 | 需要模型；v1 用层级加权顶着 |
| 检查点摘要 | 没有 | 只在部分归档时需要，v1 全量归档 |
| 向量检索 | 只有接口 | 见问题 1 |
| Context Assembly 的自适应升级 | 配置项在（`retrieval.recall.*`），`SearchService` 还没读 | 需要先有稳定的意图分析提示词 |
| 工作记忆（7 段） | 实现有，默认关闭 | 开一次多一次模型调用，只在长会话场景值得 |
| Prometheus + Grafana 部署 | 只有 `/metrics` 文本 | 输出标准格式就够，接不接是运维的事 |
| 图像 / 音频 / 视频 | 不做 | 解析交给 agent，后端只做「存附件 + 存文本 + 切分 + 摘要 + 建索引」 |
| 加密、计费、OIDC / LDAP | 不做 | 没有需求方。部署方用磁盘加密与反代解决；应用层加密会让「按 URI 直接读文件」这个基本操作失效 |
