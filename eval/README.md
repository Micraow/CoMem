# 检索质量评估

`pnpm eval` 用一份带标注的数据集测量「检索到底好不好」。它回答三个问题：

- **召回**：该找的东西有没有被找出来（Recall@k）。
- **排序**：第一个相关结果排在第几（MRR）、相关程度高的有没有更靠前（nDCG@k）。
- **代价**：一次查询要多少毫秒（p50 / p95）。

没有评估集时，改一个参数只能靠感觉；有了它，`retrieval.levelWeights`、
`retrieval.rerank.*`、`retrieval.engine` 的每一次调整都能给出「变好还是变坏」。

## 快速开始

```bash
pnpm eval                                   # 跑 eval/datasets/basic.yaml，三个引擎
pnpm eval --k 5                             # 只算前 5 名
pnpm eval --engines fts5,vector             # 只跑指定引擎
pnpm eval --json                            # 机器可读输出
```

输出是一张可以直接贴进文档的表格：

├───────────────┼───────────┼───────┼─────────┼──────────┼──────────┤
│ fts5          │     0.315 │ 0.372 │   0.335 │    0.2ms │    0.3ms │
│ vector        │     0.880 │ 0.782 │   0.777 │    1.5ms │    3.5ms │
│ hybrid        │     0.904 │ 0.852 │   0.829 │    1.6ms │    1.9ms │
│ hybrid+rerank │     0.913 │ 0.874 │   0.845 │ 8033.5ms │ 8232.4ms │
└───────────────┴───────────┴───────┴─────────┴──────────┴──────────┘

（这是本机 2026-11-08 的真实数字，数据根是临时目录，嵌入与重排都来自

### 追加对照变体

`--engines` 只选默认的三个单引擎变体；下面几个开关各自**追加**一个变体：

| 开关 | 追加的变体 | 回答的问题 |
|---|---|---|
| `--rerank` | `hybrid+rerank` | 重排到底提升多少 |
| `--hotness-weight 0.1` | `hybrid+hotness=0.1` | 热度加权是帮忙还是帮倒忙 |
| `--level-weights 1,1,1` | `hybrid+levels` | 层级先验是调好了还是调坏了 |

重排变体需要 `providers.rerank` 配好（`retrieval.rerank.enabled` 的交叉校验
要求它不是 `disabled`）。没有配置时容器创建会抛 `INVALID_ARGUMENT`，不会静默
退回「不重排」。候选文本**摘要优先、正文兜底**：摘要在索引里就有，摘要为空
（存量记忆、非记忆文件）时读正文前 512 个字符——不兜底时空文本候选会被
`applyRerank` 全部跳过，重排等于没开。

`--level-weights` 追加的是 `hybrid+levels`，与默认变体 `hybrid` 对比。层级权重
在 `hybrid` 下乘在每个后端对 RRF 融合分的贡献上（`levelWeight / (k + rank)`），
不是只改单引擎的排序分。传 `1,1,1` 就是关掉这个先验（标准 RRF），所以
`hybrid+levels` 与 `hybrid` 的差异直接回答「1.15 / 1.05 / 1.00 这组经验值在
`hybrid` 下有没有用」。

```bash
pnpm eval --config local/eval-config.yaml --rerank
```

`--config` 用一份不同的配置文件（默认 `config.yaml`），适合放评估专用的供应商。

## 数据集

| 文件 | 规模 | 用途 |
|---|---|---|
| `eval/datasets/basic.yaml` | 105 条查询 / 52 篇语料 | 当前基线，`pnpm eval` 的默认数据集 |
| `eval/datasets/basic-v1.yaml` | 34 条查询 / 23 篇语料 | 扩集前的冻结副本，只用于「新集合 vs 旧集合」对比 |

`basic-v1.yaml` 里那 23 篇文档有 22 篇的正文与 `basic.yaml` 逐字相同；
`resources/ttl-sweep.md` 在 `basic.yaml` 里补了「存在 expires_at 列里」一句
（`expires_at` 标识符查询与「许可证过期」难负例需要这个词在语料里有落点）。
除此之外，两份文件的分数差只反映**新增查询与新增语料**，不是语料被改写。

### 格式

`eval/datasets/*.yaml`（JSON 同样可以，解析后是同一个对象）：

```yaml
name: basic
description: 一句话说明这份数据集覆盖什么。

corpus:
  "comem://user/lin/memories/preferences/code-style.md": |
    代码风格偏好

    仓库统一使用 TypeScript 严格模式，缩进两个空格。

cases:
  - query: 严格
    relevant:
      - comem://user/lin/memories/preferences/code-style.md
    graded:
      comem://user/lin/memories/preferences/code-style.md: 3
```

规则：

- `corpus` 的 key 必须是合法的 `comem://` URI，且必须是**规范形态**（NFC、
  无末尾斜杠、无重复斜杠）。规范化之后与原文不同的 key 会在写入时变成另一个
  地址，标注却还是原文——两边对不上。
- 所有语料必须属于**同一个 `user` 根**。执行器把它们绑成服务图身份
  （`comem://user/{rootId}` → `user:{rootId}`）。`group` 根不支持：组作用域的
  权限依赖成员关系，评估容器没有。
- `cases[].relevant` 里的 URI 必须在 `corpus` 里，`graded` 的 key 也是。引用
  不存在的文档会在解析时抛 `INVALID_ARGUMENT`，不会静默跳过。
- `graded` 的值域是 `0–3` 的整数。没出现在 `graded` 里的 `relevant` 文档按 1 算。
- `cases` 不能为空。

**每条查询都要写清「为什么这几条相关」**（YAML 注释）。标注本身没有解释就
无法复核，而评估最容易做假的地方就是标注。

### 查询分布（105 条）

| 类别 | 条数 | 考的是什么 |
|---|---:|---|
| 中文双字词 | 28 | `unicode61` 的分词盲区：CoMem 用 CJK 单字切分 + 短语匹配覆盖 |
| 同义改写 | 56 | 没有共享连续字符时，只有语义检索能命中 |
| 专有名词 / 标识符 | 15 | 只有关键词检索能精确命中（`sqlite-vec`、`URI_CHUNK_SIZE`、`GLOB`…） |
| 分级相关性 | 3 | 一条查询对应多篇文档，相关程度不同 |
| 难负例 | 3 | 字面相似但语义无关：`记忆化缓存` / `摘要模型` / `许可证过期` |

五类合计 105 条。**`graded: 0` 的难负例一共 8 处，分布在 7 条查询里**（其中
`摘要模型` 一条挂了两个 0），不只出现在「难负例」那一类：`记忆` / `偏好` / `权限` /
`bge-m3` 也各带一个 0。上表的「条数」是**查询条数**，不是 0 值条目数。

扩集前的 34 条是同样的五类，条数 9 / 18 / 5 / 1 / 1。

### 写语料的注意事项

- 语料要真实：从项目文档、真实使用场景里取，不要 `foo` / `bar` / `lorem`。
  合成语料上的召回率没有迁移性。
- **不要把答案写进文档**。query 是「怎么配置 TypeScript 严格模式」，文档的
  标题就该是「TypeScript 严格模式配置」；在正文里写「这条文档回答了……」等于
  把查询串直接塞进索引，FTS5 的短语匹配会无条件命中。
- 难负例（`graded: 0`）要真的字面相似：`记忆化缓存` 与 `记忆` 共享字符，
  但一个讲 memoization、一个讲跨会话知识存储。

### 标注口径：主题 vs 提及

语料里**字面包含查询词**、但没有标注为相关的条目有 49 处，分布在 17 条查询上。
这是「主题」与「提及」的区分，不是漏标：一条查询问的是某个概念，只有**以它为
主题**的文档算相关，顺带出现这个词的文档不算。例如查询 `记忆` 只有
`memories/entities/comem-project.md` 是主题，`resources/ttl-sweep.md`（记忆过期
清扫）、`resources/review-gate.md`（待复核的记忆）等 8 篇只是提到。

这 49 处里落在 top-10 的会被计为误召回，`Recall@k` 因此被**有意压低**。改成
「提及也算相关」会让召回率上升，但那种口径下 `graded` 的 3 / 2 / 1 分级就没有
意义了（一篇只提到词的文档拿不到 3）。复核时按每条查询的注释判断它属于哪一种。

`中文双字词` 那 28 条里有 1 条（`校验`）的相关文档并不字面包含查询词，其余 27 条
至少有一篇相关文档含这个词。所以这一类同时考两件事：FTS5 的 CJK 单字切分能不能
命中（27 条），以及语义检索能不能补上 FTS5 的盲区（全部 28 条）。报告里要分开读。

## 指标

实现在 `src/eval/metrics.ts`，纯函数，无 IO。

| 指标 | 公式 | 来源 |
|---|---|---|
| Recall@k | `\|top-k ∩ relevant\| / \|relevant\|` | 标准 IR 定义 |
| MRR | `1 / rank_of_first_relevant`（rank 从 1 起） | 标准 IR 定义 |
| nDCG@k | `DCG@k / IDCG@k`，`DCG = Σ (2^rel_i - 1) / log2(i + 1)` | Järvelin & Kekäläinen (2002) |

两个明确的取舍：

- **`relevant` 为空时 Recall 返回 1**，不是 0。空标注表示「这条查询没有该找的
  东西」，检索没有做错任何事。返回 0 会把「数据集没标注」记成「检索失败」。
- **`graded` 为空时 nDCG 返回 0**。分子分母同时为 0，没有可归一化的基准。
  这与 Recall 的 1 不矛盾：召回率有「没有该找的」这个自然解释，nDCG 没有。

聚合是各指标的算术平均。数据集里每条查询权重相同；需要按业务重要性加权时，
拆成多个数据集跑，不要在指标层引入权重。

## 执行方式

- **每个变体一个临时数据根**（`fs.mkdtemp`）。变体之间的索引、向量、权限表
  完全隔离——否则「hybrid 比 fts5 好」可能只是「hybrid 跑在 fts5 建好的索引上」。
- **延迟只测 `find()` 调用本身**。建容器（迁移、建表、根预置）与播种语料
  （写文件 + 嵌入）在计时窗口之外。
- **每个查询跑 3 次取中位数**。第一次带冷缓存成本（SQLite 页缓存、
  `sqlite-vec`、FTS5 段缓存）；3 是「能算中位数」的最小奇数。命中取最后一次
  （热缓存稳定态）的结果。
  **W48 的嵌入缓存改变这个假设**：同一条查询的第 2、3 次会命中
  `(model, 摘要)` 缓存，中位数因此是缓存命中路径的延迟。测真实查询延迟时要
  `COMEM_PROVIDERS_EMBEDDING_CACHE_ENABLED=false`；测「用户重复问同一个问题」
  的延迟时保持默认。
- **变体切换必须重建容器**。重排 / 热度 / 层级权重 / 引擎都是容器级配置，
  没有热改入口；重建成本已经被「延迟窗口之外」隔离掉。

### 评估强制覆盖的配置

以下配置**不由** `config.yaml` 决定，评估时固定：

| 配置 | 值 | 理由 |
|---|---|---|
| `summary.generator` | `rule` | 摘要生成会调模型（一次约 10 秒），评估只关心检索；规则摘要同时保证 L0 文本可复现 |
| `session.autoCommit.enabled` | `false` | 不启动后台调度器，避免与检索无关的写入 |
| `session.expiry.idleTimeoutSeconds` | `0` | 同上 |
| `logging.level` | `fatal` | 容器日志走 stdout，会割裂表格 / JSON。执行器在变体零命中时自己补一条告警 |

## 已知限制

1. **热度变体需要访问历史。** `--hotness-weight` 会真的把配置接上，但临时数据
   根里 `access_count` 全是 0，热度分对排序没有影响。要测「0 比 0.1 好还是坏」，
   得先给语料造访问记录（例如直接改 `node.access_count` / `last_accessed_at`），
   而数据集格式目前没有这一列。这不是「没接」——是「没有数据可测」。
2. **向量变体的延迟包含查询嵌入。** `find` 在向量 / 混合引擎下要嵌入查询，远程
   供应商 300–900ms，本地 `Qwen3-Embedding-0.6B` 约 69ms（关缓存）。这是生产
   延迟的真实组成部分，但它把「索引本身多快」盖住了。要比索引延迟，看 `fts5`
   变体。
3. **`group` 作用域不支持。** 见数据集格式。
4. **评估是单用户的。** 容器绑定一个身份，语料必须属于同一个 `user` 根。
   权限过滤仍然生效（`node_permission` 的 allow/deny 谓词），但只有一组主体。
5. **没有统计显著性。** 105 条查询上的 95% 置信区间约 ±0.02（按 `0.03 ×
   sqrt(34/105)` 从扩集前的 ±0.03 折算），仍然大于「1–2 个百分点」这类改动的
   效应量。要判断这类改动，需要几百条查询，或者用同一批查询做配对比较（同一
   条查询在两个变体下的差值，方差比两条独立均值小得多）。
6. **目录不能作为语料。** 见下一节——这不是「没标」，是当前数据集格式表达不了。

### 为什么没有目录级查询

目录节点（`.../memories/preferences`）确实会进索引，但**不能作为 `corpus` 的
一条**，所以也不能作为 `relevant` 的一条：

| 位置 | 行为 | 后果 |
|---|---|---|
| `src/eval/dataset.ts:92` | key 规范化后与原文不同就抛错 | `comem://user/lin/memories/`（带末尾斜杠）被拒 |
| `src/eval/dataset.ts:102` | 语料正文不能为空 | 目录没有 L2 正文，给不出非空正文 |
| `src/eval/runner.ts:293` | `corpus` 的每个 key 都走 `filesystem.write` | 规范形态的 `.../memories` 被写成**文件**（`kind = 'document'`） |
| `src/eval/dataset.ts:175`、`129` | `relevant` / `graded` 必须在 `corpus` 里 | 隐式建出来的目录节点无法被标注 |

实测：把 `.../memories` 当 key 写会抛 `EISDIR`（路径类型不匹配）——容器启动时
已经把 `memories/` `resources/` `skills/` `sessions/` 四个上下文目录建好了。

**目录摘要本身是会生成的。** 播种时写文件会触发父目录摘要失效
（`IndexObserver.#scheduleSummaryInvalidation` → `SummaryService.markStale` →
`#invalidateDirectory`），而 `seedCorpus` 结尾的 `indexObserver.drain()` 会等它
跑完。所以 52 篇语料在 `node_fts` 里是 52 + 9 行（9 个目录），目录行的
`abstract` 非空、`content` 为空。但 `summary.generator = rule` 产出的 L0 是
「子文件名列表」（`- bge-m3.md` …），不是语义摘要——一条「用户对代码风格的
整体偏好」的查询在它上面没有可匹配的文本。

要让它可测，需要改 `src/eval/` 的两处：

1. `dataset.ts`：`corpus` 之外加一段 `directories: { URI: L0 正文 }`，并让
   `relevant` / `graded` 的校验接受目录 URI。
2. `runner.ts` `seedCorpus`：目录 key 走 `mkdir` + 写 `.abstract.md`
   （`MetadataFileStore.writeSummary`），不能走 `write`。`Container` 目前没有
   暴露元数据存储（`src/bootstrap/container.ts:504` 是局部变量），要么把它加进
   `services`，要么给 `SummaryService` 加一个写入口。

在这之前，`hybrid+levels` 与 `hybrid` 的三项指标必然逐位相同：标注里没有 L0/L1
文档，层级先验只改变 L0 记录的名次，不改变**相关文档**的名次。接线本身由
`tests/integration/services/search-hybrid.test.ts` 的「层级权重」用例钉住（同分
候选，L0 的融合贡献是 L2 的 1.15 倍）。

## 当前基线

### 本地模型（2026-11-08，`Qwen3-Embedding-0.6B` + `Qwen3-Reranker-0.6B`）

`eval/datasets/basic.yaml` 的 105 条查询 / 52 篇语料，k=10。嵌入与重排都走
`http://127.0.0.1:8089/v1`（`local-inference/`，llama.cpp GPU 后端）：

| 变体 | Recall@10 | MRR | NDCG@10 | p50 | p95 |
|---|---:|---:|---:|---:|---:|
| fts5 | 0.315 | 0.372 | 0.335 | 0.2ms | 0.3ms |
| vector | 0.880 | 0.782 | 0.776 | 1.5ms | 3.5ms |
| hybrid | 0.904 | 0.852 | 0.829 | 1.6ms | 1.9ms |
| hybrid+rerank（默认 10s 超时） | 0.902 | 0.857 | 0.835 | 10016.8ms | 10082.1ms |
| hybrid+rerank（30s 超时） | 0.913 | 0.874 | 0.845 | 8033.5ms | 8232.4ms |

**`hybrid+rerank` 的 10s 那一行撞上了超时**（`providers.rerank.timeoutSeconds`
默认值）：本地重排 50 条候选要 7.9–9.3 秒模型时间，加上候选正文读取与查询嵌入
约 1.3 秒，合计 9.2–10.6 秒，正好跨在 10 秒线上。105 条里超过一半的查询在重排
返回之前被中止、退回融合分（p50 恰好是 10016.8ms 就是证据）。它不是干净的重排
基线；把超时放宽到 30 秒后 p50 8.03 秒、不再降级，三项指标都更高。

**生产上必须知道这件事**：默认 10 秒超时 + 本地重排 + `topN=50` 会间歇性降级，
而日志被 `logging.level=fatal` 静默，用户只会看到「有时候重排没生效」。要么把
`providers.rerank.topN` 降到 20 以内（50 条 8.0 秒 → 20 条 3.6 秒），要么把
`timeoutSeconds` 提到 30 秒以上。

**延迟列要先看缓存开没开。** W48 的嵌入缓存（`providers.embedding.cache.enabled`，
默认开）让同一条查询的第 2、3 次重复命中缓存，`pnpm eval` 的 p50/p95 因此是
**缓存命中路径**的延迟（1–2ms）。关掉缓存（`COMEM_PROVIDERS_EMBEDDING_CACHE_ENABLED=false`）
后，vector / hybrid 的 p50 是 69.3ms / 68.4ms、p95 是 101.5ms / 103.0ms——那才是
「一次查询嵌入 + 一次检索」的真实代价。重排变体的延迟不受缓存影响（模型调用占
绝对多数）。

### 本地 vs 远程（34 条查询 / 23 篇语料）

同一份 `eval/datasets/basic-v1.yaml`，换嵌入与重排供应商：

| 变体 | 本地 Recall | 远程 Recall | 本地 MRR | 远程 MRR | 本地 NDCG | 远程 NDCG | 本地 p50 | 远程 p50 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| fts5 | 0.387 | 0.387 | 0.355 | 0.355 | 0.355 | 0.355 | 0.2ms | 0.1ms |
| vector | 0.985 | 0.963 | 0.905 | 0.907 | 0.903 | 0.907 | 1.5ms¹ | 371.7ms |
| hybrid | 0.985 | 0.963 | 0.923 | 0.909 | 0.929 | 0.911 | 1.7ms¹ | 357.2ms |
| hybrid+rerank | 1.000 | 0.990 | 0.895 | 0.956 | 0.913 | 0.958 | 5300.6ms | 1809.9ms |

¹ 缓存命中路径；关掉缓存后 p50 约 69ms。远程列的历史基线见下表。

**结论：嵌入持平、重排下降。**

- **嵌入**：`Qwen3-Embedding-0.6B`（596M）对 `bge-m3`（568M）参数量接近，质量差
  在 ±0.02 以内。hybrid 上 recall +0.022、MRR +0.014、NDCG +0.018；vector 上
  recall +0.022 但 MRR −0.002、NDCG −0.004。这个差落在 34 条查询的 95% 置信区间
  （±0.03）里，**视为持平**。代价是 p50 从 357ms 降到约 69ms（无缓存），并且不依赖
  网络。
- **重排**：本地 `Qwen3-Reranker-0.6B` 比远程 `Qwen3-Reranker-8B` 小 13 倍，
  MRR −0.061、NDCG −0.045，p50 从 1.81s 涨到 5.30s。更关键的是它**低于不重排的
  hybrid**（MRR 0.895 vs 0.923），也就是说在这份数据上开本地重排是负收益。

### 105 条 vs 34 条：差在语料，不在查询

同一套本地模型，三次测量（A / B 是同 34 条查询，B / C 是同 52 篇语料）：

| 设置 | 语料 | 查询 | fts5 Recall | vector Recall | hybrid Recall | hybrid MRR |
|---|---:|---:|---:|---:|---:|---:|
| A `basic-v1.yaml` | 23 | 34 | 0.387 | 0.985 | 0.985 | 0.923 |
| B 旧查询 + 新语料 | 52 | 34 | 0.387 | 0.885 | 0.895 | 0.825 |
| C `basic.yaml` | 52 | 105 | 0.315 | 0.880 | 0.904 | 0.852 |

- **A → B（只换语料，查询不动）**：vector recall −0.100、hybrid recall −0.091。
  候选池从 23 篇变成 52 篇，top-10 能覆盖的比例从 43% 降到 19%，这是分数下降的
  **主要来源**。
- **B → C（只换查询，语料不动）**：vector recall −0.005、hybrid recall **+0.009**。
  新增的 71 条不比旧的 34 条难；逐条看，旧 34 条 recall 0.895 / MRR 0.826，
  新增 71 条 0.901 / 0.864。
- **FTS5 是唯一的反例**：B → C recall 从 0.387 掉到 0.315。原因是新增的 19 条
  双字词查询比旧的 9 条难（recall 0.535 vs 0.907）：语料扩容后「提到这个词」的
  文档变多，而标注只认主题文档，被计成误召回的概率随之上升；新增的 10 条标识符
  也略降（0.900 vs 1.000）。同义改写新旧都是 0，不影响均值。

所以「105 条比 34 条低」不是标注变难了，是**候选池变大**了。跨数据集比较分数时
必须同时报语料篇数，否则 0.985 → 0.904 会被误读成「换了模型之后退步」。

### 读法

FTS5 在自然语言改写上召回低（短语匹配要求字符相邻），在专有名词 / 标识符上
召回 0.967（15 条里只有 1 条漏了一篇相关文档）；向量反过来。混合检索不是「永远更好」，它把
两者的错误率平均掉——具体哪条查询谁赢，看 `docs/operations.md` 的「检索质量评估」
一节。

分类别（本地 hybrid，105 条）：

| 类别 | 条数 | Recall@10 | MRR | NDCG@10 | 零召回 |
|---|---:|---:|---:|---:|---:|
| 中文双字词 | 28 | 0.857 | 0.860 | 0.787 | 1 |
| 同义改写 | 56 | 0.911 | 0.844 | 0.836 | 2 |
| 专有名词 / 标识符 | 15 | 0.967 | 0.956 | 0.954 | 0 |
| 分级相关性 | 3 | 0.633 | 0.833 | 0.662 | 0 |
| 难负例 | 3 | 1.000 | 0.417 | 0.529 | 0 |

「分级相关性」只有 3 条，均值被单条查询主导，不要拿它做趋势判断。零召回的 3 条
是 `校验`（语料里没有任何文档含这个词）与两条同义改写。
